# 20. Location SEO Pages — посадочные страницы по локациям и категориям

> Статус: спецификация согласована в обсуждении 2026-10-07, реализация не начата.
> Цифры по данным сняты с dev-базы на ту же дату.

## Проблема и цель

- Все листинги раздела — это фильтр: `/places?region=2&category=cave`. У такой страницы нет своего H1, текста и перелинковки, это не посадочная страница.
- Целевые запросы аудитории — «заброшки Оренбургской области», «пещеры Башкирии», «природные достопримечательности Башкортостана». Страниц под них нет.
- Цель: каждой паре «локация / категория» дать свой URL, title, H1, описание и внутренние ссылки, не ломая удобство фильтров на `/places`.

Карточки мест не затрагиваются: их URL `/places/{id}-{slug}` уже есть (миграция `2026-10-06-000002_AddPlacesSlug`). Меняются только листинги.

## Предусловия (до любых URL-изменений)

### 1. Дубли локаций от геокодера

Примерно с мая 2026 геокодер создаёт новые записи вместо того, чтобы находить существующие: провайдер начал отдавать другие названия, а сопоставление идёт по точному совпадению.

| Сущность | Старая запись | Новая запись |
|---|---|---|
| Оренбург (город) | id 1, 87 мест | id 225, 9 мест (тот же регион и округ) |
| Башкортостан (регион) | id 2 «Республика Башкортостан», 108 мест | id 78 «Башкортостан», 24 места |
| Краснодарский край | id 20 «Krasnodar Territory», 56 мест | id 89 «Krasnodar Krai», 1 место |

Всего 16 групп дублей среди городов, 36 среди районов, плюс дубли регионов (Свердловская, Липецкая, Тамбовская, Ульяновская области, Татарстан, Мордовия). Уже сейчас фильтр `?locality=1` теряет 9 мест Оренбурга.

Нужно:
- починить сопоставление в геокодере (не по точному названию, а по устойчивому признаку: OSM/провайдерский id или нормализованное имя + родитель);
- одноразовой командой слить дубли: перенести `places.*_id` на основную запись, дубль удалить;
- только после этого генерировать слаги.

### 2. Sitemap

В живом `sitemap.xml` на 2026-10-07 только 11 статических URL, ни одного места. Маршрут `/sitemap` на `main` исправлен (`2ef04cc5`), но после деплоя это нужно проверить на проде. Без рабочего sitemap новые страницы будут находиться медленно.

## Архитектура URL

### Три типа страниц на одном шаблоне

```
/places                              → все места (как сейчас)
/places/{category}                   → /places/abandoned
/places/{location}                   → /places/bashkortostan, /places/orenburg
/places/{location}/{category}        → /places/bashkortostan/cave
```

Пара «локация + категория» — отдельная страница со своим title, H1 и описанием, хотя шаблон общий.

### Правила

- **Локация всегда первой.** Иерархия «у локации есть категории» соответствует структуре сайта (локаций сотни, категорий 23). Яндекс группирует структуру по первым сегментам пути, поэтому `/places/bashkortostan/*` — это весь раздел про регион. На ранжирование по запросу порядок не влияет.
- **Один канонический URL на пару.** Обратный порядок (`/places/cave/bashkortostan`) отдаёт 301 на канонический.
- **Одна локация в пути**, самая конкретная из выбранных. Иерархия передаётся хлебными крошками, а не путём (никаких `/places/region/city/category`).
- **Одна категория в пути.** Несколько категорий — только query-параметром:
  ```
  1 категория:   /places/orenburg/abandoned                     ← индексируется
  2+ категории:  /places/orenburg?category=abandoned,military   ← noindex, follow; canonical → /places/orenburg
  ```
  Мультивыбор в UI сейчас не делаем, но правило закладываем сразу, чтобы потом не переделывать URL.
- **Метки, сортировка, пагинация, гео-фильтр** остаются query-параметрами поверх пути: `/places/orenburg/abandoned?tag=…&page=2`. Метки в SEO-путь не берём, иначе получится взрыв тонких комбинаций.
- **Уровни локации:** страна, регион, район, населённый пункт. **Районы — полноценный уровень**: у 501 из 1 166 мест есть район, но нет населённого пункта, а это и есть основной контент (горы, пещеры, заброшки вне городов).

### Порог индексации

Распределение мест на 2026-10-07:

| Уровень | 10+ мест | 5–9 | 3–4 | 1–2 |
|---|---|---|---|---|
| Регионы | 22 | 8 | 12 | 44 |
| Населённые пункты | 7 | 10 | 13 | 209 |
| Регион × категория | 25 | 37 | 37 | 247 |

Индексируются только страницы с ≥ 5 мест (порог настраиваемый). Остальные доступны пользователям, но отдают `noindex, follow` и не попадают в sitemap. Страница с 0 мест отдаёт 404, слитая локация — 301 на основную.

## Слаги локаций

### Единое пространство имён

Один слаг уникален среди **всех** уровней (страна, регион, район, город) и не совпадает с зарезервированными словами. Технически это общая таблица слагов (`slug → type, id`) или уникальный индекс поверх всех уровней.

**Зарезервировано:** слаги всех категорий, служебные пути (`create`, `edit`, `map`, `page` и т.п.), любые строки, начинающиеся с 13 hex-символов (формат id места).

### Генерация

1. Источник — только `title_ru`. `title_en` ненадёжен: встречаются кириллица («Ефремовский муниципальный округ») и мусор («Almaty respýblıkalyq mańyzdy qala»).
2. Одна фиксированная схема транслитерации (ё, й, ь, ц, щ и т.д. — раз и навсегда, не менять после запуска).
3. Тип поселения убирается из слага (`село Никольское` → `nikolskoe`), в H1 остаётся. Это 113 из 253 населённых пунктов.
4. Нижний регистр, `-` вместо пробелов и спецсимволов, без повторных дефисов, до 80 символов по границе слова.
5. Один слаг на обе локали: `/places/orenburg` и `/en/places/orenburg`.

### Коллизии

| Кейс | Пример | Правило |
|---|---|---|
| Одноимённые города в разных регионах | Париж (Челябинская обл.) и Париж (Франция); сотни сёл «Никольское» | Уточнение родителем: `parizh-chelyabinskaya-oblast`. Не цифровой суффикс `-2`: он ничего не говорит и зависит от порядка добавления |
| Кто получает чистый слаг | Если село Париж добавлено первым, оно не должно занять `parizh` навсегда | Чистый слаг выдаётся, только если имя уникально. При коллизии уточняются все одноимённые, кроме явно главного; главного назначают вручную (админка), не по принципу «кто первый» |
| Город и регион — одна территория | Москва, Санкт-Петербург, Севастополь, Минск, Алматы (уже есть в базе) | Одна сущность: страница города каноническая, регион склеен с ней 301 |
| Разные сущности с одним именем на разных уровнях | Абхазия (страна) и Абхазская АР (регион Грузии); Грузия и штат Джорджия | Приоритет на чистый слаг: страна > регион > район > город. Младший уточняется родителем |
| Одноимённые районы | «Советский район» в десятках регионов | Уточнение регионом: `sovetskiy-rayon-orenburgskaya-oblast` |
| Совпадение с категорией или служебным словом | Город «Шахты» → `shakhty` не конфликтует, но гипотетический `museum` — да | Зарезервированные слова → уточнение родителем |

### Неизменяемость и история

- Выданный слаг не меняется автоматически: ни при переименовании, ни при повторном геокодировании.
- Любая смена (ручная правка, слияние дублей, переназначение чистого слага) пишет старый слаг в таблицу истории, и он отдаёт 301 на актуальный. Без этого каждое исправление теряет накопленный вес страницы.
- Кириллица и верхний регистр в URL (`/places/Оренбург`, `/places/Orenburg/`) → 301 на канонический вид.

### Когда генерируются

- Разовая CI-команда для существующих записей (после слияния дублей).
- В геокодере при создании новой локации: сразу слаг и падежные формы.

## Морфология и шаблоны заголовков

PHP отдаёт данные, строку собирает Next.js: шаблоны принадлежат i18n-слою.

- Для локаций хранятся падежные формы (`name_genitive_ru`, `name_prepositional_ru`), генерируются библиотекой `morphos` с возможностью ручной правки, если топоним склоняется неверно.
- Формы категорий («Заброшенные места», «Пещеры», «Abandoned places») — набор фиксированный. **Рекомендация:** хранить в i18n-файлах (`public/locales/`), а не в БД — без миграции и с правкой через PR. Окончательно не решено, см. открытые вопросы.

Примеры результатов:

```
/places/abandoned            → «Заброшенные места»
/places/bashkortostan        → «Интересные места Башкортостана»
/places/bashkortostan/cave   → «Пещеры Башкортостана»
/places/orenburg             → «Интересные места в Оренбурге»
```

Description отдельный от title и содержит данные: «108 мест в Башкортостане: 18 пещер, 15 гор, 12 заброшенных объектов. Карта, фото, описания».

## Роутинг и фильтры

### Роутинг

- Flat-URL реализуется **rewrite в `proxy.ts`**: путь `/places/{x}` или `/places/{x}/{y}`, не начинающийся с 13-символьного hex-id, внутренне переписывается на одну страницу листинга. Снаружи URL остаётся плоским.
- Причина: если `/places` и `/places/[slug]` окажутся разными страницами Next.js, при каждом изменении фильтра компонент перемонтируется (моргание, сброс скролла, повторная загрузка). Через rewrite все варианты — одна страница.
- Карточка места и листинг не смешиваются в одном бандле.
- `/places/{id}/edit` не конфликтует: `edit` — статический сегмент, у Next.js он приоритетнее динамического, и id распознаётся по формату.
- Резолв слага: категория (enum) → таблица слагов → история слагов (301) → 404.

### Фильтры

- **UI фильтров в этой задаче не меняется.** Сейчас можно одновременно выбрать одну категорию и одну локацию любого уровня; этого достаточно для всех трёх типов страниц.
- Меняется только то, какой URL собирает фильтр: вместо `router.push('/places' + query)` (`pages/places/index.tsx`) — канонический путь.
- Старые query-URL отдают 301 на новые: `/places?category=abandoned` → `/places/abandoned`, `/places?region=2&category=cave` → `/places/bashkortostan/cave`; остальные параметры (`tag`, `sort`, `page`) переносятся как есть.

## Шаблон страницы

Один скелет: фильтры и список мест всегда на одном месте. Меняются заголовок и контекстные блоки.

| Блок | `/places` | `/places/{category}` | `/places/{location}` | `/places/{location}/{category}` |
|---|---|---|---|---|
| H1 | «Интересные места» | «Заброшенные места» | «Интересные места Башкортостана» | «Пещеры Башкортостана» |
| Описание | короткий вводный текст (1–2 строки) | текст категории из `category.content` | сводка по данным | сводка по данным |
| Карта | — | — | ✓ | ✓ |
| Чипы категорий со счётчиками | — | — | ✓ «Пещеры (18) · Горы (15)…» | ✓ другие категории здесь |
| Ссылки на локации | — | ✓ эта категория по регионам | ✓ дочерние районы и города | ✓ эта категория рядом |

### Описание

- У категорий текст уже есть (`category.content`).
- У локаций — **сводка, собранная из данных**: число мест, состав по категориям, дата последнего добавления. У каждой страницы свои цифры, поэтому это не шаблонная вода. Позже для топовых регионов — поле ручного текста в админке, заменяющее сводку.
- На мобильном описание сворачивается до 2–3 строк с «Подробнее»: список мест не должен уезжать за первый экран.

### Карта

- Компактное превью (~200px), Leaflet подгружается лениво, только при попадании блока в экран (Core Web Vitals, мобильный первый экран).
- Кнопка «Открыть на большой карте» → `/map` с этой локацией и категорией.
- На десктопе — сбоку от описания, на мобильном — под ним.
- На `/places` и страницах категорий карты нет: места разбросаны по всей стране, превью бессмысленно.

## Хлебные крошки и JSON-LD

Иерархия — локация, затем категория, так же как в URL.

**Листинг:**

```
/places/bashkortostan/cave:   Главная › Места › Башкортостан › Пещеры
```

**Карточка места** (визуально остаются две строки — навигация и адрес под H1, — но ссылки ведут на новые URL):

```
Главная › Места › Оренбургская обл. › Оренбург › Заброшенные › Название места
                  /places/orenburgskaya-oblast  /places/orenburg  /places/orenburg/abandoned
```

Ссылка «Категория» с карточки ведёт на страницу пары «самая конкретная локация места + категория». Сотни карточек дают этим страницам сильную внутреннюю ссылку.

JSON-LD `BreadcrumbList` в одну цепочку на всех листингах и карточках, `ItemList` — на листингах.

## SEO-паттерны

| Паттерн | Реализация |
|---|---|
| Canonical | Самоканонический путь без `sort`/`order`/гео; 2+ категорий → путь без категории |
| Пагинация | Страница 2+ — canonical на страницу 1 (решение из исходной спеки, перепроверить перед реализацией) |
| Hreflang | `/en/places/orenburg` ↔ `/places/orenburg` |
| Sitemap | Только индексируемые страницы (порог ≥ 5 мест) |
| noindex, follow | Ниже порога; 2+ категорий; гео-фильтр (уже есть) |
| 404 / 301 | 0 мест → 404; слитая или переименованная локация → 301 |

## Технические требования

### БД

- Общая таблица слагов локаций (`slug`, `type`, `entity_id`, признак «основной») с уникальным `slug`.
- Таблица истории слагов (`old_slug → type, entity_id`) для 301.
- Падежные формы в таблицах локаций: `name_genitive_ru`, `name_prepositional_ru`.
- Миграции — только новые, существующие не редактируются.

### Сервер (CodeIgniter 4)

- Исправление сопоставления в геокодере + команда слияния дублей.
- Генератор слагов (транслитерация `title_ru`, правила коллизий, резерв).
- CI-команда для разовой генерации слагов и падежей.
- Генерация слага и падежей при создании новой локации в геокодере.

**Эндпоинты:**

| Эндпоинт | Назначение |
|---|---|
| `GET /locations/resolve?slug=…` | slug → `{type, id, названия, падежи, slug, родители}` или признак 301 с новым слагом |
| `GET /places` | фильтрация по slug локации и категории, `category` принимает список через запятую |
| `GET /locations/{type}/{id}/categories` | категории с количеством мест (чипы) |
| `GET /locations/{type}/{id}/children` | дочерние районы и города (перелинковка) |
| `GET /categories/{name}/locations` | топ локаций по категории (перелинковка) |

### Клиент (Next.js)

- Rewrite в `proxy.ts` и одна страница листинга для всех трёх типов.
- Фильтр собирает канонический путь.
- 301 со старых query-URL.
- Шаблоны title/description в i18n, `yarn locales:build`.
- Контекстные блоки: описание, карта, чипы, перелинковка.
- Ссылки адреса и категории на карточке места → новые URL.
- `BreadcrumbList` и `ItemList` JSON-LD.
- `sitemap.tsx` — индексируемые листинги.

## Поэтапный запуск

**Не запускать всё одним днём.** Каждый этап переводит на новые URL целый тип страниц сразу: страницы, 301 со старых адресов, ссылки на сайте и sitemap меняются в один деплой. Нельзя допускать, чтобы часть страниц одного типа переехала, а часть нет. Между URL-этапами — пауза 2–4 недели: смотреть в Вебмастере индексацию новых URL, обработку 301, ошибки и трафик, и только потом запускать следующий.

| Этап | Что | Видно пользователю / роботу |
|---|---|---|
| 0. Данные | Фикс геокодера, слияние дублей, проверка sitemap на проде | Нет, URL не меняются |
| 1. Инфраструктура | Таблицы слагов и истории, генератор, падежи, `resolve` API, rewrite-каркас за флагом | Нет |
| 2. Категории | `/places/{category}`: H1, title, description, текст категории, крошки, 301 с `?category=` (без локации), ссылки категорий на сайте (`CategoryIcon` и др.), sitemap | Да — первый переезд |
| 3. Локации | `/places/{location}` для всех уровней: сводка, карта, чипы категорий, дочерние локации, 301 с `?country/region/district/locality=`, ссылки адреса на карточке места, порог индексации, sitemap | Да |
| 4. Комбинации | `/places/{location}/{category}`: 301 со старых комбинаций, перелинковка «другие категории здесь» / «эта категория рядом», ссылка категории с карточки места на пару, sitemap | Да |

До этапа 4 комбинации «локация + категория» остаются query-параметром на странице локации (`/places/bashkortostan?category=cave`) с canonical на `/places/bashkortostan`.

## Вне рамок этой задачи

- **Изменения UI фильтров**, в том числе мультивыбор категорий. Правило URL для 2+ категорий заложено, сам UI — потом, если в Метрике подтвердится спрос (заметная доля сессий на `/places`, где выбирают 2+ разных категорий подряд).
- **Группы категорий** («Природа», «История и культура», «Индустриальное и заброшенное», «Вода»). Перспективная отдельная задача: закрывает размытые границы 23 категорий и даёт частотные SEO-страницы («природные достопримечательности Башкортостана»). Требует продуктового решения по таксономии.
- Ручные тексты для локаций в админке.
- og:image для листингов (статическая карта с точками мест).
