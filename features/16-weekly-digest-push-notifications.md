## Web push notifications

Built (2026-10-14); the decisions below describe how it works. Web only (there is no mobile app).

**What is pushed.** Activity on the user's places — comment, photo, rating, edit, cover,
bookmark, visit (the email types) — plus a new achievement and a new level (push only).
"+N experience" is never pushed. Settings keys `push{Type}` next to `email{Type}`
(`Config\Notifications::$channelTypes`), all on by default; they matter only once the user
enabled push on a device.

**Push instead of email.** When a push about an event was delivered, the email about the
same event is not sent (`rejected`, "Delivered as push or seen on the site"; a push dropped because the user saw the notification on the site counts too). While the push is still waiting
(grouping, quiet hours) the email waits too; when the push fails, the email goes. The weekly
digest is email only and not affected.

**Pacing.** A push waits a minute first: if the user is on the site, the toast shows the
notification and marks it read, and the push is dropped ("Seen on the site"). After a push
about places, the next ones within 15 minutes are grouped into one ("3 new events on your
places"). Quiet hours 23:00–08:00 in the time zone of the user's device: activity pushes
wait for the morning and come as one. Achievements and levels follow the user's own action
and are not held.

**Asking.** Never on page load and never the browser prompt first. After the user's first
meaningful action (a place, a photo, a rating, a comment) a card offers "Get comments on your
places right away": Enable (then the browser prompt) / Not now (again in 14 days) / Don't
offer (`localStorage`). Not shown when push is unsupported, blocked, already on, or on iOS
outside an installed app. Settings (`/users/settings`) have a "Push on this device" block —
state, Enable / Turn off, "Send a test" — and a column of push switches next to email.

**iOS.** Web Push works only in a site added to the Home Screen (iOS 16.4+): in Safari the
settings explain how to add it instead of an Enable button.

**Devices and accounts.** A subscription belongs to the user who enabled it on that device;
several devices per user. Signing out from the menu removes the device's subscription.
`pushsubscriptionchange` in the service worker re-subscribes and moves the record (matched by
the old endpoint).

### Server

- `minishlink/web-push`, VAPID keys in `.env` (`push.vapidPublicKey`, `push.vapidPrivateKey`,
  `push.vapidSubject`), generated by `php spark push:vapid`.
- `push_subscriptions` (user, endpoint + its hash, keys, time zone, locale, user agent, last
  success, failures) and `push_messages` — a queue like `sending_mail` (same states, claim,
  retries, grouping), sharing the queue code with it (`QueueRows`).
- `NotifyLibrary::push()` — every in-app notification — queues the push (`PushQueue`) when the
  type is pushable, the user wants it and has a device.
- `notifications:send` sends emails, then pushes; an email about an event whose push is still queued waits for its outcome;
  410/404 from the push service deletes the subscription; the daily cleanup also deletes old
  push messages and subscriptions that keep failing.
- API: `GET /push/key`, `POST /push/subscriptions` (auth), `DELETE /push/subscriptions` and
  `POST /push/subscriptions/renew` (by endpoint, no auth: the service worker has no token),
  `POST /push/test` (auth).

### Client

- `public/sw.js`: `push` (show the notification: title, body, icon, image, tag, url),
  `notificationclick` (focus an open tab and go to the url, or open one),
  `pushsubscriptionchange`.
- `utils/push.ts` + `hooks/usePushSubscription.ts`: support, permission, subscribe, unsubscribe.
- `PushPrompt` card in the layout, triggered by successful place / photo / rating / comment
  requests (`applicationSlice`); the settings block and the push column.
